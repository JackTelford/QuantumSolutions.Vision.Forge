# Cinematic Studio

Vision.Forge turns a brief into a finished film or still with code: HTML and CSS, Three.js and Blender render the frames, ffmpeg assembles and checks them, and you direct the shots and review the rendered contact sheets. This file is the router. The creative knowledge base under `references/` is read only when a step needs it.

## What it does and does not do

It does:

- Take a brief such as "a 15-second studio product film of a frosted-glass bottle" and produce a treatment, a shot list with real camera, lens, lighting and composition parameters, one still per shot for review, the full render and an H.264 delivery.
- Keep one look across every shot and lane: one physical camera model, one lighting cookbook, one finishing grade.
- Render deterministically: a frame is a function of its frame number, and the same inputs on the same machine produce the same pixels.

It does not (say so up front, then offer the stylized or abstract alternative):

- Photoreal people, faces or animals, or a live-action look.
- Generative image or video models, paid or keyed APIs, or music from the internet: music is user-supplied or absent.
- Byte-identical frames across machines; quality gates between machines use SSIM and PSNR.
- EEVEE without an interactive desktop session: the blender lane then falls back to Cycles, which is slower.
- Narration in any language but English. Narration uses a small local voice model that is installed separately on request; the user's own recording is always the alternative.
- Glass, liquid, fabric or a brushed texture: a product body is an opaque coated material in the look's primary colour on both 3D lanes, a cap a satin metal in the highlight colour. Say so in the treatment's substitutions before the first still.

## The one command

Every operation that touches a renderer, ffmpeg or the file system goes through one program:

```
node "${CLAUDE_PLUGIN_ROOT}/scripts/cli.ts" <command> --data-dir "${CLAUDE_PLUGIN_DATA}" --out <dir>
```

`${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` and `${CLAUDE_PROJECT_DIR}` are substituted by Claude Code when it loads this file, so by the time you read this they are absolute paths. They are not environment variables of the shell you run commands in, and the CLI never reads them from the environment: always pass `--data-dir` and `--out` explicitly, exactly as above, and keep the quotes (on Windows the substituted paths use forward slashes, which Node accepts). `--out <dir>` is where deliverables go: pass `--out "${CLAUDE_PROJECT_DIR}/out"` unless the user names a directory. Caches, tool records and browser profiles stay under the data directory; a command the user runs by hand (for example `doctor` from the README quick start) must pass the same `--data-dir "${CLAUDE_PLUGIN_DATA}"` to share those caches, otherwise run `doctor` again through this skill. Nothing else is ever run: no `npm`, no `npx`, no direct `ffmpeg` or `blender` call.

Add `--pretty` to read a result by eye, `--quiet` to silence progress and `--verbose` for detail. Progress and errors go to standard error; standard output carries the result only.

## Reading a result

Standard output carries exactly one JSON object:

- `ok`: `true` when the command succeeded.
- `command` and `data`: the command name and its payload; each command documents its shape.
- `artifacts`: absolute paths of files produced for the user. `evidence`: absolute paths of reports and contact sheets.
- `errors[]`: on failure, one entry with `code`, `message` and `hint`. `message` says what went wrong and `hint` says what to do next; repeat both to the user.

Exit codes: `0` success, `1` failure, `2` usage or not yet implemented (a `usage` error: fix the invocation; a `not-implemented` error: the hint names the milestone, tell the user and stop), `130` cancelled by the user (run the command again to resume; finished shots are kept).

## First step: doctor

The first command of every session is `doctor`. It finds ffmpeg and ffprobe, Microsoft Edge or Google Chrome, the GPU and, optionally, Blender 5.2, records their paths and versions in `tools.json` under the data directory, and lists which lanes can run. Until it reports `ok: true`, do not plan or render.

Read its result as follows. `data.lanes` has one boolean per lane (`html`, `three`, `blender`, `audio`); plan only with lanes that are `true`. `data.missing` lists `{ tool, hint, required }` for every program it did not find; Blender is `required: false`. `data.problems` holds warnings in plain sentences, such as an unsupported Blender version, a software WebGL renderer or a non-interactive desktop session; repeat them to the user when they touch the piece being made. `ok: false` with code `tool-missing` means a required program is absent: repeat the hint, which is the exact install command, and stop. Pass `--require <lane>` when the piece needs one lane in particular; the command then fails with the same code when that lane cannot run.

## The order of a production

This is the whole flow from a prompt to a delivery. Every command reads and updates `<out>/<jobId>/job.json`, so the job folder is the state of the production; nothing after the four documents is written by hand. Worked examples with their documents and commands are under `examples/product-film/` (four blender shots, a text plate) and `examples/explainer/` (seven html shots timed to a narration, captions burnt in).

1. **The questionnaire.** Fill the director's questionnaire of `references/direction/treatment-template.md` from the user's words into a `brief` document: use case, goal, audience, length, frame, tempo, emotion, palette hints, the text that must appear verbatim, the subject and its primitive, narration and music, and `limitsAcknowledged`. Where the prompt is silent take the default the template names, write it into the brief and say it once. Ask at most one question, and only when two readings would give materially different films. Scan the prompt against `references/direction/steering-table.md`: every hit becomes a substitution.

2. **The treatment gate.** Write the one-page treatment (the `treatment` document: logline, the look and why, the beats with a lane and a length each, the substitutions, the risks) and show it to the user as the template's page before any render. Wait for a yes when the piece is a judged one; otherwise state it in two sentences and go on. A substitution the user has not heard is a defect.

3. **The shot list.** Build the `shot-spec` from the treatment: one row per shot with size, angle, lens and f-stop (`references/cinematography/`), one dominant move from the catalogue with its window inside the shot, the rig from `references/lighting/cookbook.md` (one rig per film, per-shot overrides only), a composition anchor, the text elements inside title safe with the reading hold, and the transitions by the grammar of `references/editing/pacing-and-transitions.md`. The delivery is the shots minus the overlaps; land on the brief's length by the last hold, never the hero. Lanes: `blender` for a product when `doctor` reports it, `three` for stylized 3D or when Blender is absent, `html` for type, charts and 2.5D stages; the name or a label over a 3D shot is a text element of that shot, rendered by the html lane as a plate over the picture (see `still` and `render`). A loopable piece ends on a hold or a breathe at the same framing its first shot starts from, with its text gone by the last frame. A `low` angle (15 degrees below the subject's centre) on a product shorter than about half the camera distance puts the camera under the stage floor and renders black on the blender lane: give such a product stature with a longer lens and the `thirds-bottom` anchor instead.

4. **The look.** Take the preset `references/color/look-bible.md` names for the use case and emotion unless the brief names colours or fonts; then start from the nearest preset, change the palette and at most two other tokens, and say which. One look per film.

5. **`doctor`, `assets`, `plan`.** `doctor` first (every session), then `assets --fetch` for the HDRI every rig of the shot list maps to (`1k` for the browser lanes, `2k` as well for a blender shot; the brief's `subject.assetIds` may name them so `plan` refuses to run without them), then `plan`. Fix every problem in the documents, never in the job folder, and repeat every warning to the user.

6. **The still loop.** For every shot: `still`, then look at the finished still and the 100 percent crops of every text box and of the subject, then judge by `references/direction/review-rubric.md`: the measured checks are authoritative, and before any pass name three faults (there are always three). Fix what costs less than a re-render of the shot in the shot spec or the look, `plan` again and `still` again; at most three rounds per shot, after which the design changes (size, lane, lighting), not the parameters. The job id is the hash of the four documents, so an edited shot spec plans into a new job folder; earlier folders keep their rounds, and a folder whose documents are unchanged keeps every pinned profile and approval. Run `sheet` over `<job>/stills/` and read the sheet for continuity between neighbours; never approve from the sheet alone.

7. **Approval.** `still --approve` for each shot whose still passed the gate and the rubric. `render` refuses a shot that is not approved under its current key.

8. **The render and its estimate.** Before `render`, tell the user the frame count and the estimate: about 110 ms per 1080p frame for the browser lanes (600 frames in about 70 s); a blender shot costs seconds per frame (1.3 to 1.8 s per 1080p frame with EEVEE on the owner's RTX 2060, the close-up at f/2.8 the slowest; 465 frames in 11.5 minutes; more with Cycles), and `render` measures a ceiling on each blender shot's first three-frame batch (1.8 to 4 times the measured rate). Wait for a yes on a render over 60 seconds; a cancelled render resumes where it stopped.

9. **Narration**, when the brief asks for it: `audio install --yes` on the user's yes, then `audio synth` before the shot durations are locked, because the sentences are the clock; the WAV and SRT go under `<job>/narration/` with `--out <job>`, where `assemble --job` finds them.

10. **`assemble --job`, then `qa --job`.** The plan is built from the job: no assembly plan is written by hand. Read the QA report's `checks[]`; never pass a piece the report failed.

11. **Say what was made.** Give the user the delivery path, the QA summary (every check with its measured value, the failing ones first), the stills and sheets as evidence, and the limits that applied (the substitutions, the lanes used, a still that passed on its third round). Never claim a shot looks right without having looked at the frame.

## Commands available now

- `plan --brief <file> --treatment <file> --shot-spec <file> --look <file>`: validates the four documents, checks them against each other (ids, beats and their lanes, fps and size, the transition arithmetic, the pacing rules) and runs the composition solver's geometric checks on every shot; writes `<out>/<jobId>/` with copies of the four documents and `job.json` (`evidence[0]`), one key per shot. The job id is the first eight characters of the content hash of the four documents, so the same documents always plan into the same folder and an edited document plans into a new one. `data.warnings` lists pacing and composition warnings (a lens focused away from the subject names the distance to set); repeat them to the user. Exit 1 with code `cross-document` or `schema-validation` lists every problem as a sentence: fix the documents, never the job folder. Asset ids named in the brief or shot spec must already be in the ledger, so run `assets` before `plan`.
- `still --job <folder or job.json> --shot <id> [--frame <k>] [--renderer hardware|software|any] [--scale <n>]`: renders one frame of the shot through the lane and the harness exactly as `render` will, grades it like the delivery (no grain), runs the still gate (composition checks 1 to 5 with the look's type scale, the browser's own measurement of every text box, WCAG contrast behind every text box on the finished still, average luma inside the look's band) and pins the render profile into the job folder's shot spec, which changes the shot's key once. Writes `<job>/stills/<shot>-r<round>.png` (`artifacts[0]`), the raw frame beside it as `<shot>-r<round>.raw.png`, `<shot>-r<round>.gate.json` (`evidence[0]`) and, with `--scale 2`, a 4K `<shot>-r<round>-2x.png` (a full render at twice the size; a blender shot takes about a minute). A three or blender shot with text elements renders its text plate too: the html lane's words over transparency, kept as `<shot>-r<round>.text.png`, and the finished still is the graded picture with the plate laid over it, so the gate judges the composite (`data.textStillPath`; null for an html shot or a shot without text). The default frame is the one where the last text element has finished entering (else the end of the camera move, else the middle). Exit 1 with code `still-gate` lists every failing check: fix the shot spec or the look, never the still, and run again. `still --job <...> --shot <id> --approve` marks the latest passed still approved; `render` refuses shots that are not. A `blender` shot runs the attempt ladder of ADR 0004 inside `still` (EEVEE on OpenGL, EEVEE on Vulkan, Cycles on OptiX, CUDA, then the CPU, which is legal for stills only); the rung that rendered is pinned as the profile and `render` runs that rung alone. Its still renders into the round's scratch folder with more samples and denoising, so it is never a cached frame. Blender codes: `blender-script` (the applier's Python raised: the message carries the traceback's tail), `blender-render` (Blender ran but the frames are not right: a non-zero exit, a missing or black frame, a fresh crash log; a black frame on every rung means the camera sees nothing, for example a `low` angle under the floor), `blender-timeout` (a batch overran its time limit); each names the scene document and the logs it kept under the cache. Other codes: `still-rounds` (the three-round cap: change the shot's design), `lane-unavailable` (the lane has no renderer on this machine: run `doctor`), `renderer-mismatch` (pass `--renderer any`), `page-init` and `page-seek` (the page's own sentence; report it), `browser-profile-in-use`, `data-file` (run `doctor` first).
- `render --job <folder or job.json> [--shot <id>] [--renderer hardware|software|any] [--frames <a-b>] [--force] [--allow-unapproved]`: renders every frame of every approved shot (or the named one) into `<data dir>/cache/<key>/frames/f%06d.png` with a render manifest beside them (`evidence[]`): one browser for all the html and three shots, and Blender in batches of thirty frames per process for the blender shots (never while the browser is capturing); frames already in a complete manifest are reused, `--force` re-renders. A three or blender shot with text renders its text plate right after its picture, under the plate's own key, through the run's browser, resumable like any shot; the shot counts as rendered when both are complete. `data.shots[]` carries `framePattern` (the picture's pattern), `textFramePattern` (the plate's; null for an html shot or a shot without text), `frames`, `msPerFrame`, `reused` and, for a blender shot, `estimate` (`secondsPerFrame`, `totalSeconds`, measured on its first three-frame batch and a ceiling, since that batch carries Blender's start); `data.estimate` sums them. Confirm before a long render (rule 5): quote the frame count and the estimate first, then the measured rate after the first batch. Codes: `shot-not-approved` (run `still` and `still --approve` first), `render-profile-mismatch` (the still gate pinned another renderer or engine, or `--renderer` disagrees with the pin), plus the still command's browser and Blender codes.
- `assets [--list] [--fetch <id,id>] [--all] [--verify] [--credits] [--credits-path <path>]`: the pinned catalogue of CC0 Poly Haven HDRIs (`hdri:<name>-1k` and `-2k`, ten entries). `--list` (the default) shows what is installed; `--fetch` downloads named ids into `<data dir>/assets/hdri/` through the allowlisted downloader, verifies size and MD5 and records the ledger (`assets.json`); `--verify` re-hashes installed files (exit 1 code `asset-integrity` names a changed file, which is set aside so `--fetch` downloads it again); `--credits` writes `CREDITS.md` with every downloaded asset and the four bundled OFL fonts. Fonts (Inter, Space Grotesk, Playfair Display, JetBrains Mono) ship with the skill and need no download. The rig-to-HDRI mapping: `product-studio`, `three-point-soft`, `high-key`, `butterfly`, `overcast-soft` and `soft-cross` use `studio_small_09`; `window` and `rembrandt` `brown_photostudio_02`; `low-key`, `split`, `rim-only`, `contre-jour`, `practical-glow` and `neon-rim` `studio_small_03`; `golden-hour` `kloofendal_48d_partly_cloudy_puresky`; `neon-night` `moonless_golf`.
- `audio install [--yes] [--verify]`, `audio status`, `audio voices`, `audio synth --text "<sentences>" | --script <file.txt> [--voice af_heart] [--fps 30] [--gap 0.35] [--out-dir <dir>]`: the optional narration component (ADR 0007). `install` without `--yes` prints what it would install (about 150 MB of packages compressed, 92 MB of weights) and the third-party notices (eSpeak NG under GPL-3.0-or-later, libvips under LGPL-3.0-or-later, a proprietary DirectML.dll that is present but not used) and exits 0 with `data.confirmed false`: show that to the user and run again with `--yes` only on their yes; with `--yes` it installs into `<data dir>/narration/` (resumable; `data.weights[].verified` is `downloaded`, `rehashed` or `ledger`; `evidence[0]` is `provenance.json`; codes `npm-missing`, `npm-install-failed`, `weights-download-failed`). `status` reports `installed`, `packagesPresent`, `weightsPresent[]`, `missing[]`, the ledger records and the provenance without touching npm or the network. `voices` lists the offered English voices with their grades (`af_heart` default). `synth` normalizes the text (numbers, units, currency, abbreviations), reads one sentence at a time, writes `<out>/narration/narration.wav` (24 kHz mono, −16 LUFS, −1.5 dBTP), `captions.srt` and `narration.json` (`artifacts` wav and srt, `evidence[0]` the json) whose `sentences[]` carry `startFrame`/`endFrame` at the fps asked, plus `totalFrames`, `loudness` and `directMlMapped`; for an explainer run it before the shot durations are locked, since the sentences are the clock, and pass `--out <job>` so `assemble --job` finds the files under `<job>/narration/`. Codes: `narration-not-installed` (hint: `audio install --yes`), `voice-unknown` (the hint lists the voices), `narration-load-failed` and `narration-synthesis-failed` (the component is present but the model or a sentence failed; hint: `audio install --verify`, or reword the sentence), `narration-loudness`, `narration-sample-rate`, `data-file`. Narration is English only; always offer the user's own recording as the alternative.
- `validate <file>`: checks any pipeline document (brief, treatment, shot spec, look bible, job, assembly plan, QA report, assets ledger) against its schema and the semantic rules of its kind; the error lists every problem as a sentence. Asset ids named in a brief or shot spec must already be in the ledger under the data directory.
- `assemble --job <folder or job.json> [--music <file>] [--music-gain <dB>] [--burn-in] [--codec h264|hevc|prores] [--out-file <path>]`: builds the assembly plan from the job and encodes the delivery. One clip per shot in shot-spec order from the shot's render cache (a shot that is not rendered under the job's key with a complete manifest fails with code `shot-not-rendered`: run `render` first), the text plate of a three or blender shot as the clip's overlay, laid over the graded picture before the transitions and the grain (ADR 0008 decision 4), the shot spec's transitions (a `dissolve` is the linear cross-fade), the narration `audio synth --out <job>` wrote under `<job>/narration/` with its captions (burnt in with `--burn-in` in the look's body face, its text colour on its background colour at 60 percent, 36 px with a 72 px margin at 1080p, scaled with the height; else the SRT beside the delivery), the music the user supplied (ducked under narration, `--music-gain` in dB, −12 by default), the look's grade baked to `<job>/grade.cube`, and `<job>/<jobId>.mp4` (`.mov` for ProRes) as the delivery at CRF 16, preset medium, faststart. The plan is written to `<job>/assembly-plan.json` (`evidence[0]`) and the job moves to `assembling` and then to `qa` with its delivery recorded. `artifacts` holds the delivery and its `.srt` when the plan has captions; `data.verified` holds the probed frame count, frame rate and size. `assemble --plan <assembly-plan.json>` takes a plan written by hand instead (no job is touched; the `--job` options are refused with it).
- `qa --job <folder or job.json> [--report <file>] [--loudness-target <LUFS>] [--no-fail]`: measures the delivery `assemble --job` recorded against the plan it wrote: dimensions, fps and duration, exposure drift, black frames, frozen frames outside the planned holds (the last half second of every clip, and the whole of a clip whose shot holds by design with `static-hold` or `breathe`: a 2.5D stage under a breathe is frozen to the pixel, and that is not a stuck render), pops away from the planned cuts, the text contrast behind every text element of every shot at the clip's first frame and at the frame the still gate judged, and every shot's approved still, as its raw frame, against frame k of the shot's render in the cache (SSIM 0.98 or higher: the comparison before the grade, the grain and the encode; a shot without a still or a manifest is not compared and the report's entry says why), plus loudness and true peak when there is audio. The report goes to `<job>/qa/<jobId>.qa.json` (`evidence[0]`); the job becomes `delivered` when every check passes and `failed` otherwise. Exit 1 with code `qa-failed` names the failing checks unless `--no-fail` is given; code `job-not-assembled` means `assemble --job` has not run. Read the report's `checks[]` and repeat each failing check's `detail` to the user; never pass a piece the report failed. `qa --video <file> [--plan <file>] [--text-boxes <json>] [--still <png> --still-frame <k>]` measures any file the same way without a job.
- `sheet --frames <dir of PNGs or JSON list> | --video <file> [--every <n>] [--output <png>] [--columns <n>] [--thumb-width <px>]`: tiles labelled frames into one contact sheet (`artifacts[0]`). Look at the sheet before judging a shot. `--frames` takes PNGs (a directory, or a JSON list `[{ "path", "label" }]`): a sheet over `<job>/stills/` shows the finished stills, and a sheet over a shot's render cache shows that shot's picture frames before the grade, the text plate, the grain and the transitions. `--video <delivery> --every 15` takes one frame every half second of the finished piece (extracted under `<out>/sheets/<name>-frames/`, labelled by frame number): look at that sheet after `assemble --job`, and at 100 percent crops of the transitions and the text, before telling the user the piece is done.

## Behavior rules

1. Ask at most one clarifying question before starting. Otherwise choose sensible defaults, state them and go.
2. Never claim a result is photoreal, or that a shot looks right, without inspecting the rendered frames or the contact sheet. Say what you saw, and name three faults per still before a pass.
3. State the limits up front when the brief asks for people, faces, animals or a live-action look, and propose the stylized or abstract alternative before any render.
4. Narration uses a small local voice model that the user installs on request; always offer the user's own recording as the alternative. Music is user-supplied or absent.
5. Confirm before a long render: give the frame count and the time estimate, and wait for a yes.
6. Never invent asset ids, file paths or tool versions. Use only what a command returned.
7. Fail loudly: when a command fails, repeat its `message` and `hint`, say which step stopped, and never pretend the step succeeded or silently skip it.

## Blender rule

Run `doctor` first. If Blender is missing or is not 5.2.x, say so, offer the setup script (`Setup-VisionForge.cmd` or `scripts/setup.ps1 -Install` on Windows, `scripts/setup.sh` elsewhere; it asks for approval and installs about 350 MB) and continue with the `html` and `three` lanes. Never download Blender yourself and never run a Blender build the user did not install. When the user declines Blender, pass `-SkipBlender` (or `--skip-blender`) so the script installs only what the other lanes need.

## Status

Implemented today (M7): `help`, `version`, `doctor`, `validate`, `plan`, `still`, `render`, `assets`, `assemble`, `qa`, `sheet` and `audio` (the narration component, installed on request); the `html` lane renders (title cards, lower thirds, kinetic type over a 2.5D stage with a stand-in for the subject, and the text plates of the 3D lanes) and the `three` lane renders (the subject's primitives as PBR materials on a cyc under the cookbook's rigs as area lights, an HDRI or room environment, depth of field from the lens, motion blur from the shutter, bloom from the look's halation, AgX or standard tone mapping). A `three` shot uses the HDRI its rig names when `assets --fetch` has installed it and the built-in room environment otherwise; `plan` warns when a shot's `lens.focusDistanceM` leaves the subject out of focus and says the distance to set. The `blender` lane renders when `doctor` finds Blender 5.2 (the same subject, rig, camera and look as the three lane, as a closed scene document applied by one logic-free Python file; EEVEE or Cycles chosen by the still gate's ladder; the rig's HDRI as the world when it is installed). Text over a three or blender shot is a plate of its own, composited after the grade by `still` and `assemble`; `assemble --job` and `qa --job` run the whole delivery from the job folder. The full productions through these commands are `examples/product-film/` (record under `docs/evidence/m7/`) and `examples/explainer/` (record under `docs/evidence/explainer/`). `help` prints the live table with every option. The state of the whole repository, with what is and is not verified, is in `docs/handoff.md` at the plugin root: `${CLAUDE_PLUGIN_ROOT}/docs/handoff.md`.
